# Рядом — руководство для разработчиков

Mobile-first приложение для совместного разделения ресторанного чека. Клиент: Svelte 5, TypeScript и Vite. Данные, защищённые изменения, платежи и realtime: Supabase.

## Локальный запуск

```sh
npm install
npm run dev
```

Приложение всегда работает с Supabase, локального режима нет. Укажите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в `.env` (пример — `.env.example`): для разработки подходит и рабочий проект, тестовые чеки сами удалятся через 3 дня. Для нового проекта включите Anonymous Sign-ins в Authentication и примените миграции из `supabase/migrations`. Клиент использует только publishable/anon key; `service_role` key добавлять нельзя.

Миграции создают нормализованные таблицы, RLS-политики и ограниченные RPC-функции. Гости открывают общую ссылку на чек и присоединяются под своим именем без отдельного приглашения.

## Реализовано

- Вход по ссылке без вопросов: гость сразу попадает в чек под именем из прошлых чеков или под тремя случайными буквами («XMA»). У себя он видит «вы» и поле с этим именем в плейсхолдере; новое имя (`rename_participant`, только своё) видят все, и оно запоминается для следующих чеков.
- Создание чека без формы: «Создать» сразу открывает системный выбор фото (камера или галерея, `src/lib/photo.ts`). Распознанные строки попадают в таблицу «Название · Кол-во · Цена» на странице создания; если фото не выбрали, таблицу заполняют вручную (Enter в цене переходит на новую строку). Процент обслуживания берётся из чека или вписывается вручную. Имя создателя — сохранённое с прошлых чеков или три случайные буквы, название — «Ужин 7 октября»; оба меняются потом. После «Готово» сразу открывается QR-код и ссылка. Позиции хранят порядок добавления (`items.position`), так что скан идёт в порядке чека.
- Скан чека: после съёмки владелец рамкой из четырёх углов выделяет только список блюд и итог (`ScanReceiptModal.svelte`; углы тянутся пальцем с лупой или стрелками, первая рамка — светлая бумага на фото, `suggestArea`). `src/lib/ocr.ts` по этим углам перспективным преобразованием рисует область ровным прямоугольником шириной ~1400 px, так что ни угадывания наклона, ни поиска бумаги при чтении нет, а шапка, подвал и стол вокруг не читаются. Распознаёт Tesseract.js (русский + узбекский) прямо на устройстве, проходами до тех пор, пока прочтения не сойдутся (`settled`): как есть, с выровненным освещением (каждый пиксель делится на среднюю яркость вокруг), с выпрямленными строками для изогнутой бумаги (наклон строк меряется в плитках по резкости профиля, `bendOf`), затем колонкой строк (ловит крупный жирный «ИТОГО») и в чёрно-белом. Первое прочтение меряет шрифт: узкий высокий шрифт кухонных принтеров (ширина буквы меньше 0,42 высоты) перечитывается растянутым по горизонтали до обычных пропорций, иначе Tesseract путает цифры («9 000» → «3000»). Слова и строки с низкой уверенностью отбрасываются, широкий промежуток между словами становится табуляцией — разделителем колонок. `src/lib/receipt.ts` разбирает текст на позиции: форматы «2 x 25 000 = 50 000», «45 000 x 2», «Кол-во ⇥ Сумма» и «Кол-во ⇥ Цена» (по заголовку таблицы, а без него — по тому, какое прочтение сходится с итогом), названия над ценой и на нескольких строках, разделы меню, обслуживание («Надбавка», процент без суммы, строка после итога), скидку, подытог и итог строкой ниже надписи; коды MXIK и штрихкоды, деление счёта на гостей и всё после итога игнорирует. Числа не подгоняются под итог: из чисел строки берётся только то, что на ней напечатано (количество — из цены и суммы строки), а количество исправляется лишь при типичной путанице OCR 1↔7 и 1↔4, когда с ним сходится итог. `bestReading` выбирает прочтение, которое сходится с итогом, а иначе самое близкое к нему (лишние строки сверх итога весят вдвое), и при необходимости берёт итог из другого прочтения. Если позиции дают больше итога и без одной-трёх строк сходятся — с них снимаются галочки; строка без прочитанного названия остаётся пустой, владелец вписывает его сам, сверяясь с фото. Worker, WASM-ядро и языковые модели (~10 МБ) Vite-плагин `tesseractAssets` в `vite.config.ts` берёт из `node_modules` и раздаёт с самого сайта по адресу `tesseract/`, без CDN. Модели после первой загрузки кэшируются в IndexedDB.
- Независимое распределение каждого экземпляра позиции поровну целыми UZS. Произвольные доли из старых чеков считаются, но в интерфейсе их больше не задают.
- Service fee с детерминированным распределением остатка округления.
- Presence и уведомления об изменениях через Supabase Realtime: база шлёт одно broadcast-сообщение на транзакцию в приватный канал чека, клиент перезагружает чек одним вызовом `get_check`.
- Платежи: создатель платит по счёту целиком, остальные отмечают, сколько уже отдали ему, и видят остаток. Полная сумма уходит создателю на подтверждение, меньшая считается частичной оплатой.
- Создатель может указать карту или телефон для перевода (`checks.payment_details`); гости видят их в итогах и копируют без пробелов. Оплата — это галочки, без сумм и частичной оплаты: участник ставит или снимает ✓ «я оплатил» (`mark_paid`), создатель ставит ✓✓ (`confirm_payment`) — после ✓ участника или без неё — и может снять её (`unconfirm_payment`). После ✓✓ участник свою отметку не меняет. Если доля участника выросла, отметка снимается. Собственная доля создателя считается оплаченной: он платил по счёту.
- «Поровну на всех» (`share_item_equally`): создатель делит все порции позиции между всеми, кто сейчас в чеке, заменяя прежние отметки.
- Создатель редактирует позицию (`update_item`: новая цена делит каждую порцию поровну между теми, кто её отметил; меньшее количество убирает последние порции) и сам чек (`update_check`: название и процент обслуживания). Оплаты, которых после изменения не хватает, снова открываются.
- Чек — одна страница, как напечатанный: таблица «Название · Кол-во · Цена», под каждой строкой — кто её взял. Одна порция — кнопка «Моё» (сколько угодно людей, цена делится поровну); несколько — счётчик своих порций и имена остальных «вагончиками» с числом порций («Бек 4½»), ряд прокручивается вбок. Нажатие на чужое имя делит с этим человеком одну его порцию пополам. «На всех» включает только создатель, после этого позицию никто не отмечает. Ниже — итог по людям: ✓ гость указал сумму перевода, ✓✓ создатель подтвердил (нажатием на человека); новая сумма от гостя снимает подтверждение. Номер карты гостю не показывается: пока он должен, внизу висит кнопка «Скопировать карту».
- На главной у каждого сохранённого чека виден статус («Вам должны», «С вас», «Все рассчитались»), чек можно убрать из списка на этом устройстве. Имя запоминается для следующих чеков.
- PWA: `public/manifest.webmanifest`, иконки и `public/sw.js` (страницы — сначала сеть, собранные файлы и OCR-движок — из кэша). Service worker регистрируется только в production-сборке.
- Срок хранения: общий чек живёт 3 дня (`public.check_lifetime()` и `checkLifetimeDays` в `src/lib/limits.ts`). Просроченный чек сразу недоступен, а удаляется при создании следующего чека (`purge_expired`, по 20 за раз) вместе со всем, что в нём есть: участниками, позициями, долями, оплатами и привязками устройств. В чеке показывается дата удаления.
- Анонимный аккаунт живёт 10 дней с последнего использования (`public.account_lifetime()`): клиент продлевает его вызовом `touch_account` не чаще раза в час, `create_check` и `join_check` продлевают его сами. Неиспользуемые аккаунты удаляет тот же `purge_expired`; участники в чеках при этом остаются.
- Лимиты (`src/lib/limits.ts` и миграции `202610040003`, `202610050001`): 50 участников, 100 позиций и 1000 порций на чек, цена порции не больше 100 000 000 UZS, не больше 20 новых чеков на анонимный аккаунт за сутки, длины названий и имён как в базе.
- Секрет создателя не попадает в адресную строку: он хранится в `localStorage` браузера, где создан чек. Старые ссылки с `#p=` ещё принимаются, но адрес сразу очищается. Чек управляется из того браузера, где его создали; гость, открывший ссылку в другом браузере, — новый гость.
- Если Supabase-сессия потеряна, клиент входит заново и возвращает этот браузер к его участнику: создателя по секрету, гостя по токену входа из `localStorage`.
- Клиент работает с базой только через RPC: прав на чтение и запись таблиц у `anon` и `authenticated` нет. В Realtime-канал чека участники пишут только presence; broadcast шлёт сама база.
- Копирование сводки, сохранение изображения, печать в PDF и удаление закрытого чека.
- GitHub Pages workflow с SPA fallback `404.html`.

## Проверки

```sh
npm run check
npm test
npm run build
```

Качество сканера меряется на настоящих фото: `npm run scan:receipts` (или `node scripts/scan-receipts.ts [имя] [--all] [--text]`) запускает `ocr.ts` и `receipt.ts` в headless Chromium так же, как приложение, и сравнивает строки с напечатанными. Фото лежат в `receipts/` (приватно, в git не попадают), а `receipts/expected.json` для каждого описывает рамку, которую поставил бы владелец, итог, процент обслуживания и позиции: `{ "area": [[x, y] × 4], "total", "servicePercent", "items": [[название, кол-во, цена], …] }`. `--all` читает все проходы и оценивает каждое прочтение, `--text` печатает выбранное; подробности — в `receipts/results.json`. Chromium берётся из `$CHROMIUM` или из Playwright.

Unit tests проверяют разбор распознанного текста чека (форматы сумм, фискальные строки «2 x 25 000,00», весовой товар, названия на нескольких строках, ошибки OCR, тексты настоящих чеков), округление по суммам, индивидуальные экземпляры одинаковых позиций, произвольные доли, service fee, нераспределённую стоимость, мгновенную отметку до ответа сервера, маршруты, определение платформы для установки и тексты ошибок. SQL-тесты в `supabase/tests` применяют все миграции к PGlite (Postgres в WASM) с заглушками схем Supabase и проверяют RPC, права доступа, broadcast и обновление существующих данных.

## GitHub Pages

Сайт публикуется только при новом релизе (см. «Версии и релизы» ниже): `.github/workflows/release.yml` вызывает `.github/workflows/deploy.yml` с новым тегом. Передеплоить вручную можно в **Actions → Deploy to GitHub Pages → Run workflow**, указав тег (например, `v0.2.0`) или оставив поле пустым для выбранной ветки. В настройках репозитория откройте **Settings → Pages** и выберите **GitHub Actions** в качестве источника публикации. В **Settings → Secrets and variables → Actions → Variables** добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (Supabase project URL и publishable/anon key). Эти значения публичны в браузерном приложении; `service_role` key сюда добавлять нельзя.

Для Supabase создайте проект и включите **Authentication → Sign In / Providers → Anonymous Sign-Ins**. Workflow `.github/workflows/supabase-migrations.yml` применяет новые миграции при изменениях в `supabase/migrations` на `main`/`master`; его также можно запустить вручную. Для подключения добавьте в **Settings → Secrets and variables → Actions** секреты `SUPABASE_ACCESS_TOKEN` (Supabase personal access token) и `SUPABASE_DB_PASSWORD` (пароль базы данных), а в **Variables** — `SUPABASE_PROJECT_REF` (ID проекта из URL панели Supabase). Если схему уже применяли вручную через SQL Editor, workflow сам это обнаружит (таблица `public.checks` есть, а в истории миграций нет `202610010001`), пометит начальную миграцию как применённую и затем применит остальные. Запустить его вручную можно в **Actions → Apply Supabase migrations**. В **Authentication → URL Configuration** добавьте URL опубликованного GitHub Pages сайта в **Site URL** и **Redirect URLs**. Для публикации сайта настройте переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, затем запустите workflow Deploy to GitHub Pages.

## Версии и релизы

Версии ведёт [release-please](https://github.com/googleapis/release-please) по сообщениям коммитов ([Conventional Commits](https://www.conventionalcommits.org/ru/)):

- `fix: …` поднимает patch (`0.2.0 → 0.2.1`), `feat: …` поднимает minor (`0.2.1 → 0.3.0`), `feat!: …` или `BREAKING CHANGE:` в теле поднимает major. Коммиты `chore:`, `docs:`, `refactor:`, `test:` версию не меняют.
- После каждого мержа в `master` workflow **Release** открывает или обновляет PR `chore(master): release x.y.z` с новой версией в `package.json`, `.release-please-manifest.json` и записью в `CHANGELOG.md`.
- Когда пора выпускать, смержите этот PR: появятся тег `vX.Y.Z` и GitHub Release, и тот же запуск опубликует сайт.

Чтобы release-please мог открывать PR, включите **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**.

Версия и короткий хеш коммита подставляются при сборке (`define` в `vite.config.ts`) и видны внизу главной страницы.

Миграции Supabase по-прежнему применяются сразу после мержа в `master`, ещё до релиза, поэтому они должны быть совместимы с уже опубликованной версией сайта.
